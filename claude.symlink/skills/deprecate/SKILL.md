# /deprecate — 程式碼是負債，不是資產

每一行程式碼都有持續成本：測試、文件、安全更新、相依升級、以及每個路過的人的心智負擔。
程式碼的價值來自它提供的功能，不是程式碼本身。

多數團隊很會蓋東西，很少團隊會拆東西。這支處理的是後者。

---

## 兩條會決定成敗的原則

**Hyrum's Law 讓移除變難。** 使用者夠多時，**所有可觀察的行為**都會有人依賴 ——
包含 bug、時序特性、沒寫在文件裡的副作用。所以淘汰需要**主動遷移**，不是發個公告。
別人沒辦法「就換過去」，因為他們依賴的行為替代品沒有複製。

**淘汰計畫從設計時就開始。** 蓋新東西時就問：「三年後要怎麼把它拆掉？」
介面乾淨、有 feature flag、對外表面積小的系統，才拆得掉。

---

## Step 1 — 先回答五個問題

```
1. 它還提供獨有的價值嗎？        → 有就繼續養。沒有才往下。
2. 有多少消費端依賴它？          → 把遷移範圍量化出來。
3. 替代品存在嗎？                → 不存在就先蓋替代品。沒有替代品不准淘汰。
4. 每個消費端的遷移成本多少？    → 能自動化就直接做；要手動且很貴就跟維護成本比。
5. 不淘汰的持續成本是多少？      → 安全風險 + 工程師時間 + 複雜度的機會成本。
```

⚠️ **量測用量，不要憑感覺。** 這台機器上：`rg` / `ast-grep` 掃 codebase，
有 telemetry 就查實際呼叫量，公開套件就看下載數。「應該沒人用了」不是證據。

## Step 2 — 選強制或建議

| 類型 | 什麼時候用 | 機制 |
| --- | --- | --- |
| **建議性** | 遷移可選，舊系統還穩 | 警告、文件、推一把。使用者按自己節奏遷。 |
| **強制性** | 有安全問題、擋住進度、或維護成本不可承受 | 硬期限 + **你要提供遷移工具與文件** |

**預設走建議性。** 強制性不是「公告一個死線」就算數 —— 沒有遷移工具、文件與支援，
那只是把成本轉嫁出去。

## Step 3 — 遷移

### 3.1 先有替代品

替代品必須：涵蓋舊系統所有關鍵用途、有文件與遷移指南、**已經在正式機上跑過**
（不是「理論上比較好」）。

### 3.2 公告與文件

```markdown
## 淘汰公告：OldService

**狀態**：自 2026-03-01 起淘汰
**替代品**：NewService（見下方遷移指南）
**移除日期**：建議性，尚無硬期限
**原因**：OldService 需要手動擴容且沒有觀測性，NewService 兩者都自動處理。

### 遷移指南
1. `import { client } from 'old-service'` → `from 'new-service'`
2. 更新設定（範例如下）
3. 跑驗證腳本：`pnpm migrate-check`
```

### 3.3 一個一個遷，不要一次全遷

每個消費端：找出所有接觸點 → 換成替代品 → 驗證行為一致（測試、整合檢查）→
移除對舊系統的引用 → 確認沒有回歸。

⚠️ **Churn Rule**：你擁有那個被淘汰的基礎設施，**你就有責任遷移你的使用者** ——
或提供不需要任何遷移的向後相容更新。不能公告完就把問題丟給別人。

### 3.4 最後才刪

所有消費端都遷完之後：確認零使用（metrics、log、相依分析）→ 刪程式碼 →
連同測試、文件、設定一起刪 → 移除淘汰公告 → 慶祝（刪程式碼是成就）。

⚠️ 這台機器上刪檔用 `rip`，不要用 `rm`。

## 遷移模式

| 模式 | 適用 | 做法 |
| --- | --- | --- |
| **Strangler** | 有流量可以切分 | 新舊並行，流量 0% → 10%（canary）→ 50% → 100% → 刪舊 |
| **Adapter** | 消費端太多，改不動 | 用舊介面包新實作，消費端不動，後端先換 |
| **Feature flag** | 要逐一切換、可快速回退 | `if (flags.isEnabled('new-service', { userId }))` |

## 資料庫 schema：一律 expand/contract

schema 變更是最危險的遷移，因為**資料是唯一不能靠 revert 部署回滾的東西**。

失效模式很固定：把 schema 變更跟程式碼變更綁在同一次發版。
改欄位名的同時開始用新名字 —— 在 rollout 那段新舊程式同時在跑的視窗裡，
一定有一邊在查一個不存在的欄位。

**解法：永遠不要就地改欄位。** 用累加式的階段推進，讓新舊程式在**每一步**都合法。

```
EXPAND ──────────→ MIGRATE ─────────→ CONTRACT
新增可為 null 的     分批回填舊資料，    確認沒人讀舊欄位後，
新欄位，與舊欄位     應用層同時雙寫      在「另一次」部署裡刪掉
並存
```

**把 `name` 改成 `full_name` 的實際步驟**：

1. **Expand** — 新增可為 null 的 `full_name`。部署。（舊程式無視它，什麼都不會壞）
2. **雙寫** — 應用層每次 insert/update 同時寫 `name` 和 `full_name`。部署。
3. **回填** — 分批把 `name → full_name` 補完，**不要一次 UPDATE 幾百萬列鎖表**。
4. **切讀** — 改讀 `full_name`，繼續雙寫。部署，觀察一段時間。
5. **Contract** — 停寫 `name`，然後在**另一次、更後面的部署**裡才 drop 欄位。

每一步都可獨立部署、可獨立回滾：第 4 步出事，回滾程式碼即可，`full_name` 還在被寫。

**規矩**：

- **累加優先，破壞性最後而且單獨一次部署。** 新增（可為 null 的欄位、新表、新索引）
  在任何一次部署都安全；drop 與 rename 要等到**沒有程式碼引用舊結構**之後，自己一次部署。
- **每個 migration 都要有測過的 down。** 不能反向的 migration 等於不能回滾的部署。
  合併前就把 `down` 寫好並跑過。
- **回填分批、限流、離開熱路徑。**
- **大索引用不阻塞寫入的方式建**（Postgres：`CREATE INDEX CONCURRENTLY`）。

## 殭屍程式碼

沒有人維護、但每個人都依賴的程式碼。徵兆：

- 6 個月以上沒有 commit，但仍有活躍的消費端
- 沒有指定的維護者
- 一直紅的測試沒人修
- 有已知漏洞的相依沒人升
- 文件引用著已經不存在的系統

**處理方式只有兩種**：指派一個負責人並好好維護，或者訂出具體遷移計畫淘汰它。
不能留在中間狀態 —— 要嘛投資，要嘛移除。

## 常見的自我開脫

| 你會這樣想 | 事實 |
| --- | --- |
| 「它還能跑，幹嘛刪？」 | 沒人維護的可運作程式碼會累積安全債與複雜度，維護成本悄悄長大。 |
| 「以後可能會用到」 | 以後真的要，重建就好。留著沒用的程式碼比重建更貴。 |
| 「遷移太貴了」 | 拿遷移成本跟兩三年的維護成本比。長期幾乎都是遷移比較便宜。 |
| 「等新系統做完再來淘汰舊的」 | 淘汰計畫在設計時就要開始。新系統做完時，你已經有新的優先事項了。 |
| 「使用者會自己遷過去」 | 不會。提供工具、文件與誘因，或者你自己動手遷（Churn Rule）。 |
| 「兩套系統可以一直並存」 | 兩套做同一件事 = 雙倍的維護、測試、文件與新人上手成本。 |
| 「就改個欄位名，一行而已」 | rollout 期間新舊程式同時跑，一定有一邊查到不存在的欄位。expand/contract，不要就地改。 |
| 「新增欄位跟刪舊欄位放同一個 migration」 | 那是把安全的 add 綁上破壞性的 drop。drop 要自己一次部署。 |
| 「rollback 要用再寫」 | 沒有 down 的 migration 就是不能反向的部署。合併前寫好並跑過。 |

## 紅旗

- 淘汰了但沒有替代品
- 只有公告，沒有遷移工具與文件
- 「建議性淘汰」掛了好幾年，進度是零
- 有活躍消費端的無主程式碼
- 還在往已淘汰的系統加新功能（該投資的是替代品）
- 沒量測用量就開始淘汰
- 沒確認零使用就刪程式碼
- schema 變更跟依賴它的程式碼在同一次部署上線
- 就地 rename / drop 欄位，而不是走 expand/contract
- migration 合併時沒有測過的 down；回填會鎖表

## 驗收

- [ ] 替代品已在正式機驗證過，涵蓋所有關鍵用途
- [ ] 遷移指南存在，有具體步驟與範例
- [ ] 所有活躍消費端都已遷移，**而且用 metrics/log 驗證過**
- [ ] 舊程式碼、測試、文件、設定都完整移除（用 `rip`）
- [ ] codebase 裡沒有殘留引用（`rg` / `ast-grep` 掃過）
- [ ] 淘汰公告已移除（它的任務結束了）

schema 遷移額外檢查：

- [ ] 變更以累加階段推進（expand → 回填 → contract），不是單次就地修改
- [ ] 每個部署步驟，新舊程式碼對 schema 都合法
- [ ] 每個 migration 都有測過的 down；回填分批且限流
- [ ] 破壞性步驟（drop / rename）在沒有程式碼引用舊結構之後，單獨一次部署
